# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

"Biosoft" is a tool for Biodanza facilitators to plan classes ("clases"): sequencing music tracks into exercises ("ejercicios"), grouping exercises, and playing them back with fade-in/fade-out, crossfade ("empalme"), clipped start/end, and repeat controls. The repo has three mostly-independent parts that share only the music-collection folder conventions:

1. **`UI-react/`** — the app under active development, and where nearly all current feature work happens. React + TypeScript + Vite rewrite of the old AngularJS app, opened via `file://` with zero server. See "React app architecture" below.
2. **`UI/`** — **deprecated**, the original AngularJS 1.x app being replaced by `UI-react/`. Don't invest in it beyond what's asked.
3. **.NET (`Biodanza.Model`, `Hyperlinks`, `HyperlinkTests`, `Hyperlinks/Hyperlinks.sln`)** — **deprecated**, the maintainer's old offline tooling for preparing Excel-based music catalogs. Don't invest in it beyond what's asked.

## React app architecture (`UI-react/`)

Must keep working opened directly from disk via `file://`, zero server, ever. That ruled out `type="module"`/runtime `fetch()`/`import()` (blocked under `file://` by Chrome/Edge CORS) and drove the stack: **React + TypeScript + Vite + `vite-plugin-singlefile`** (bundles everything — JS, CSS, fonts as data URIs — into one self-contained `dist/index.html`), **Zustand** for state, **React Router in `HashRouter` mode** (`src/App.tsx`). Bootstrap 3 Cerulean CSS for styling. See [UI-react/vite.config.ts](UI-react/vite.config.ts) and [UI-react/README.md](UI-react/README.md) for the build-config rationale in full.

- **Dev loop**: `npm install`, `npm run dev` (normal Vite dev server, not `file://`-constrained), `npm run build` (produces the real artifact, `dist/index.html` — **verify by double-clicking it from Explorer**, not `npm run preview`, which uses a server and can mask `file://`-only bugs). `npm run lint` runs `oxlint`. **`npx tsc -b --force` is the only reliable typecheck** — plain `tsc --noEmit` can silently reuse a stale incremental build-info cache and miss real errors.
- **Routes** ([UI-react/src/routes.tsx](UI-react/src/routes.tsx)): `/clases`, `/clase/:id`, `/ejercicios`, `/musicas`, `/cargarMusica`, `/cargarEjercicios`, `/etiquetas`, `/acercade` — each backed by a component in `src/pages/`.
- **State/data — no backend**. Zustand stores in `src/store/`: `dataStore.ts` (ejercicios/musicas/colecciones/grupos, `Record<id,T>` + ordered id arrays), `clasesStore.ts`, `playerStore.ts` (audio playback), `alertStore.ts`, `etiquetasStore.ts`. Persistence is `localStorage` via [UI-react/src/lib/storage.ts](UI-react/src/lib/storage.ts), keys prefixed `ngStorage-biosoft_*`.
- **Playback**: `src/store/playerStore.ts` + `src/components/PlayerControls.tsx` — a singleton `<audio>` element created once via `document.createElement` (not a React ref) so it survives route changes; fade-in/out, clipped start/end, and "empalme" (NOT real crossfade — pause-then-advance).
- **Search/ranking**: `src/lib/search.ts` — weighted-token, accent-insensitive (`.normalize('NFD')`) search; replicate this normalization approach if extending search.
- **Escanear Carpeta clave detection** ([UI-react/src/lib/clavesEscaneo.ts](UI-react/src/lib/clavesEscaneo.ts)): when importing a music collection by scanning a folder (no Excel), derives each file's real `CD:pista` clave either from a catalog Excel at the scanned root (same shape as "Organizacion de archivos de musicas" below) or, failing that, from folder/file name masks (see that section). A collection can override the generic masks with its own `MascaraCarpetas.txt`/`MascaraArchivosMusica.txt` at its root.
- Music audio files are **not** in this repo — referenced by relative path at runtime, from an external "coleccion" folder tree.

**⚠️ `dist/musica/` is a directory junction, not a real folder**: kept pointing at the maintainer's real music collections (`build.emptyOutDir: false` in `vite.config.ts` exists specifically so a rebuild doesn't wipe it) so `cargarMusica`/the player can be tested against real audio. **Never bulk-copy or generate test fixtures into `dist/musica/` (or anywhere resolved through it) — it silently writes into the maintainer's real, un-backed-up collection.** If a test needs a folder Vite can serve, create an isolated one elsewhere under `dist/` (e.g. `dist/test-scan-root/`) and delete it when done; if it truly needs to live under the real tree, add a scoped temp folder directly under the real music root and remove it right after — don't fight the junction, and never `cp -r`/`rm -rf` a whole `dist/musica/...` tree.

There is no test suite for `UI-react/`. The established verification pattern: launch headless Chrome (`chrome.exe --headless --disable-gpu --remote-debugging-port=<port> --user-data-dir=<scratch>`, add `--allow-file-access-from-files` if a test needs to `fetch()` local `file://` resources, e.g. to fabricate a `File`/`FileList` for an upload input) and drive it via raw CDP over the native `WebSocket` global (Node 22+, no puppeteer needed) against the real `dist/index.html` build — not `npm run dev`, not mocks. Notes learned the hard way: `DOM.setFileInputFiles` **does not work on `webkitdirectory` inputs** in headless Chrome (silently attaches 0 files) — instead build a real `File`/`DataTransfer` in-page (`fetch('file:///...')` → `Blob` → `new File(...)`, override `webkitRelativePath` via `Object.defineProperty`) and assign it to the input's `.files` before dispatching a `change` event. Always kill the debug Chrome instance by PID (`netstat -ano | grep ":<port>"` → PowerShell `Stop-Process -Id <pid> -Force`), never `taskkill /IM chrome.exe` (kills the user's other Chrome windows too).

## Root-level scripts and data

- `deploy.cmd` / `deployWithoutMusic.cmd` / `deploy musicaBsAs.cmd` / `deploy musicaIBF.cmd`: package the deprecated `UI/` (plus external music folders on the maintainer's `D:\Google Drive\Biodanza\...`) into distributable zips with 7-Zip. These reference maintainer-specific absolute paths and are not portable — don't "fix" the hardcoded paths without confirming with the user, they're intentional for this deployment workflow.
- `*.sql` files at the root and in `Queries/`/`UI/app/data/` are ad-hoc queries/migrations against the (deprecated-app-era) `Biodanza` SQL Server DB; they aren't wired into any migration framework.
- `cimeb/`, `Ajustes Ejercicios.sql`, `ArchivosTest/` hold reference/source catalog data (e.g. `cimeb_catalogo_ibf_2012_espanol.docm`, `BsAs.xls`) used when building or cross-checking music collections — treat as fixtures/reference data, not code.

## Organizacion de archivos de musicas
Dentro de la carpeta musicas, estan la colecciones de musica. Cada carpeta es una coleccion. Dentro de cada carpeta debe haber un archivo NombreCarpeta.xlsx. En el archivo esta el mapeo de musicas con ejercicios y con la ubicacion del archivo. Todas las pestañas deben tener la misma info solo que ordenada de diferente manera. LAs pestañas que tienen las columnas archivo y carpeta son las que sirven. Generalmente primer columna de cada pestaña tiene la clave de la musica. Dicha clave tiene 2 partes que identifican numero de  carpeta y numero el archivo separadas por un . o un - o :
Para la carpeta tenes que ver que empiece con ese numero. Para el archivo puede ser que enmpiece por ese numero o por el numero de carpeta y luego el numero de archivo. El excel debe tener correctamente mapeado cada musica con la ubicacion en disco indicada por las columnas carpeta y archivo

Algunas carpetas de colección además tienen, en su raíz, `MascaraCarpetas.txt`/`MascaraArchivosMusica.txt`: una lista de máscaras tipo `0{cd}*`, `{coleccion} {cd}*`, `0{pista}*`, `Track No?{pista}.mp3`, etc. que documentan cómo se arman los nombres reales de carpeta/archivo de ESA colección a partir de su número de CD/pista. `UI-react/`'s "Escanear Carpeta" las usa (si están) en vez de una lista genérica — ver `UI-react/src/lib/clavesEscaneo.ts`.
